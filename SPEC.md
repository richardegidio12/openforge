# OpenForge Specification

> This document defines what OpenForge is, what each component must contain to be valid, and the rules for extending or changing the method. It is the source of truth for contributions and design decisions.
>
> Changes to this spec require an ADR in `docs/decisions/`.

---

## What OpenForge is

OpenForge is a **structured, AI-driven method for building data platforms**. It consists of:

1. **Personas** — specialized AI experts, each responsible for one phase or concern of the data project lifecycle
2. **Skills** — cross-cutting principles applied by multiple personas
3. **Templates** — artifact schemas that personas produce and consume
4. **Artifacts** — filled instances of templates, saved to the user's project folder. Includes `PROJECT-CONTEXT.md`, the session compaction artifact that enables cross-session continuity
5. **Workflows** — documentation of how components connect
6. **MCP integrations** — optional tool connections that extend the Agent's capabilities
7. **Examples** — worked instances of a complete project using the method

---

## Persona spec

A valid OpenForge persona must contain all of the following sections, in this order:

```
# Persona: [Name]

## Identity
[Who this persona is, what they do, their primary value]

## When to invoke
[Specific triggers — what must exist before this persona is called]

## What you consume
[List of required and optional input artifacts]

## What you produce
[List of output artifacts]

## Applied skill: [Skill Name]    ← if applicable
[How the skill applies in this persona's specific context]

## Behavioral instructions
### Tone and style
### [Domain-specific principles]

## Process
[Numbered blocks or phases within the persona's session]

## Output format / artifact structure
[What the generated artifact must contain]

## Warning signals
[Specific patterns that indicate risk — the persona must flag these]

## Activation Prompt
[The exact prompt the user pastes to activate this persona]
```

**Rules for personas:**
- Each persona has exactly one primary artifact (or a defined set for dual-mode personas)
- The activation prompt must be self-contained — no external context required
- Personas do not invoke other personas directly (artifact-mediated communication, per ADR-002)
- Phase-specific personas have a defined position in the sequence; transversal personas do not (per ADR-003)
- Every new persona requires an update to the Orchestrator routing tree

## Skill spec

A valid OpenForge skill must contain:

```
# Skill: [Name]

> *Applied by: [list of personas]*

## The core principle
[One paragraph — the "why" of this skill. Must include a quotable principle.]

## [Principle sections]
[3-10 named principles, each with ❌ anti-pattern and ✅ correct pattern]

## Quick reference checklist
[Actionable checklist — the minimum to apply this skill on any story/artifact]
```

**Rules for skills:**
- Skills are cross-cutting — a skill that applies to only one persona should be embedded in that persona instead
- Skills contain principles and patterns, not process steps (process lives in personas)
- Skills include both code examples (when applicable) and the reasoning behind each principle
- The "core principle" must be expressible as a single quotable sentence
- Every skill must be referenced in `.cursor/rules/openforge.mdc` for Cursor Agent Mode

---

## Template spec

A valid artifact template must:
- Contain every section the corresponding persona is expected to fill
- Use `[placeholders]` for all values the user/persona fills in
- Include a header note: `> 📝 *Artifact generated by the **[Persona Name]** persona.*`
- Have a clear status field (`Draft` / `Approved` / `In progress`)
- Be usable as a checklist (key sections have `- [ ]` checkboxes where applicable)

---

## Artifact lifecycle

```
Template → Persona fills it → Draft artifact → Human approves → Approved artifact
                                                     ↑
                                              May be revised
                                          (CHANGE MODE triggers revision)
```

An artifact is **approved** when:
- The persona has completed its session
- The human has reviewed the output
- It has been saved to the project folder

An artifact is **stale** when:
- An upstream artifact it depends on has been revised
- The Orchestrator (CHANGE MODE) has flagged it for re-evaluation

## The dependency graph

```
data-product-brief
    └→ architecture-document
         ├→ cost-context
         └→ security-assessment
              └→ data-contract-[name] + governance-policy
                   └→ pipeline-spec
                        └→ [build: code + runbooks]
                             ├→ quality-signoff
                             └→ security-signoff
```

Any change to an upstream artifact may invalidate downstream artifacts. The Orchestrator's Change Impact Matrix (in `personas/00-orchestrator.md`) is the authoritative mapping.

## Contribution rules (spec-driven development)

OpenForge follows **spec-driven development**: the spec is updated before the implementation.

### Adding a new persona
1. Open an issue describing the persona, its role, inputs, and outputs
2. Update this SPEC.md to include the new persona in the dependency graph (if phase-specific) or mark it as transversal
3. Write an ADR if the new persona introduces a design decision that affects the method architecture
4. Write the persona file following the Persona spec above
5. Update `personas/00-orchestrator.md` routing tree
6. Update `workflows/full-project-flow.md`
7. Update `README.md` personas table
8. Update `.cursor/rules/openforge.mdc` if the persona changes Cursor Agent behavior
9. PR with all of the above — partial implementations not accepted

### Adding a new skill
1. Open an issue describing the skill, what principles it covers, and which personas it applies to
2. Write the skill file following the Skill spec above
3. Add "Applied skill" sections to all relevant personas
4. Update `.cursor/rules/openforge.mdc` cross-cutting skills section
5. Update `README.md` skills table
6. PR with all of the above

### Adding a new MCP integration
1. Verify the MCP server package exists (or commit to maintaining a community one)
2. Document in the appropriate `mcp/[group].md` file following the existing format
3. Add to `mcp/cursor-mcp-config.json`
4. PR with documentation + config only — no changes to persona files required

### Changing an existing persona
1. If the change affects the persona's contract (inputs, outputs, or routing): update SPEC.md first
2. If the change affects a design decision: write an ADR
3. If the change affects downstream personas: update all affected personas
4. Update the example in `examples/` if the change would produce a different artifact

### Changing a skill
1. A skill change propagates to all personas that reference it — verify each one still applies correctly
2. Update the checklist in the skill file
3. Update `.cursor/rules/openforge.mdc` skill summary
4. PR must include: skill file + all affected persona files + cursor rule
