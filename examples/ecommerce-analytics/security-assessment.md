## Findings

### 🔴 Critical — No secrets management strategy defined

**Risk:** The architecture document describes credentials for ERP PostgreSQL and the Google Sheets service account but does not specify where these will be stored. Hardcoded credentials in code or CI/CD environment variables are a frequent cause of data breaches.

**Affected component:** All ingestion connectors (HIST-004, HIST-005, HIST-006) and CI/CD pipeline.

**Remediation:**
- Use **GCP Secret Manager** for all credentials: ERP connection string, Google Sheets SA key, any API keys.
- Dagster jobs inject secrets at runtime via the Secret Manager API — never via hardcoded env vars or config files.
- GitHub Actions uses GCP Workload Identity Federation (preferred) or a dedicated CI SA key stored in GitHub Secrets (not in the repository).
- `dbt profiles.yml` added to `.gitignore` — never committed.

**Story to add to pipeline-spec:**
> **SEC-001 (Epic 0 — Setup):** Configure GCP Secret Manager and inject all credentials via secrets — no hardcoded values anywhere in the codebase or CI/CD YAML.

---

### 🟡 Important — Single service account pattern not confirmed

**Risk:** The architecture document references a "service account" but does not distinguish between ingestion, transformation, and BI service accounts. A single SA with broad permissions is a common misconfiguration that violates least privilege.

**Affected component:** HIST-001 (GCP environment setup), Metabase configuration.

**Remediation:** Create separate SAs with minimum permissions:
| SA | Permissions |
|----|------------|
| `ingestion-sa` | GCS write (Bronze only) + Secret Manager read |
| `transformation-sa` | GCS read (Bronze) + BigQuery read/write (Silver, Gold) |
| `bi-sa` | BigQuery read (Gold only) — used by Metabase |
| `ci-sa` | Terraform apply + Dagster deploy — no data access |

**Story to add to pipeline-spec:**
> **SEC-002 (Epic 0 — Setup):** Create dedicated service accounts per pipeline component with minimum permissions as defined in the security assessment.

---

### 🟡 Important — Metabase connection endpoint not specified

**Risk:** If Metabase connects to BigQuery via a public IP, it exposes the data endpoint to the internet. Self-hosted Metabase on a GCP VM should connect via private Google APIs (VPC Service Controls or Private Google Access).

**Affected component:** ADR-006 (Serving layer), Metabase configuration.

**Remediation:**
- Enable **Private Google Access** on the VM subnet where Metabase is hosted. This allows BigQuery connections without traversing the public internet.
- Confirm that the Metabase VM is not itself publicly exposed (no public IP, or if it has one, protected by IAP or VPN).

**Story to add to pipeline-spec:**
> **SEC-003 (Epic 5 — Governance):** Confirm Metabase connects to BigQuery via Private Google Access. Document network configuration.

---

### 🟡 Important — Bronze layer access controls not explicitly defined

**Risk:** If analysts can query the Bronze layer directly (e.g., via BigQuery console), they can access raw PII fields (customer CPF, phone, email) before anonymization happens in Silver.

**Affected component:** ADR-003 (Data layers), HIST-005 (customers ingestion).

**Remediation:**
- BigQuery IAM: `bronze` dataset — `dataViewer` for `transformation-sa` only. No analyst access.
- Document this rule in HIST-001 acceptance criteria and HIST-014 (Access Controls).

**Note:** This is already partially addressed in HIST-014, but must be enforced from Epic 0, not as an afterthought in Epic 5.

---

### 🟢 Recommended — Enable BigQuery audit logging

**Risk:** Without audit logging, there is no way to detect unauthorized data access after the fact. Required for LGPD incident response.

**Remediation:**
- Enable **BigQuery Data Access audit logs** (DATA_READ, DATA_WRITE) for the `silver` and `gold` datasets in production.
- Set log retention to 90 days minimum.
- Export logs to Cloud Logging (already included in GCP free tier at current volume).

**Story to add to pipeline-spec:**
> **SEC-004 (Epic 5 — Governance):** Enable BigQuery audit logging on Silver and Gold datasets in production. Set 90-day retention.

---

### 🟢 Recommended — Define credential rotation policy

**Risk:** Long-lived credentials that are never rotated increase the blast radius of a potential leak.

**Remediation:**
- Document a rotation policy for the ERP service account and Google Sheets SA key (suggested: every 90 days).
- Add to `governance-policy.md` operational section.
- For future consideration: GCP Workload Identity Federation eliminates long-lived SA keys entirely.

## Security baseline confirmed ✅

- **GCS bucket is not publicly accessible** — bucket-level IAM confirmed in architecture. Uniform bucket-level access will be enforced (HIST-001).
- **Encryption at rest** — GCP default encryption at rest applies to GCS and BigQuery. No configuration needed; confirmed active.
- **Encryption in transit** — all GCP services enforce TLS. ERP PostgreSQL connection uses SSL (confirmed in architecture stack table). Google Sheets API uses HTTPS.
- **No public data exposure in Gold** — Metabase SA will have read-only access to `gold` dataset only. Silver and Bronze are not reachable from the BI layer.
- **IaC in git** — Terraform in the repository (HIST-001, HIST-003). Infrastructure changes are version-controlled and reviewed on PR.
