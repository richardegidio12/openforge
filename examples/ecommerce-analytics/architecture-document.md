## 1. Context

The project aims to replace a manual ERP report export process with an automated pipeline that makes sales data available in Metabase by 07:00 daily. Volume of ~2,000 orders/day with peaks of 8,000. The company's existing stack is GCP. Team of 2 data engineers.

## 3. Architectural Decision Records (ADRs)

### ADR-001: Processing strategy
- **Decision:** Daily batch
- **Rationale:** All use cases identified in the brief are satisfied with D-1 data available by 07:00. No use case requires latency under 1 hour. Batch radically simplifies the architecture and operations.
- **Accepted trade-offs:** No intra-day analysis. If a need for real-time monitoring arises (e.g. live campaign), the architecture will need to be revisited.
- **Discarded alternative:** Near-real-time with micro-batch every hour — 3x complexity with no identified benefit.

### ADR-002: Storage
- **Decision:** GCS (landing/Bronze) + BigQuery (Silver and Gold)
- **Rationale:** Company already uses GCP. BigQuery eliminates compute management, scales automatically, has native SQL, and native integration with Metabase and dbt. GCS as landing zone preserves raw data and serves as a fallback.
- **Accepted trade-offs:** Per-query cost in BigQuery (on-demand). Mitigated by low volume (~2k orders/day) and use of partitioning.
- **Discarded alternative:** Snowflake — additional cost with no technical advantage for a GCP user.

### ADR-003: Data layers
- **Decision:** Bronze (GCS) → Silver (BigQuery) → Gold (BigQuery via dbt)
- **Rationale:** Volume and complexity justify 3 layers. Bronze preserves raw data for auditing and reprocessing. Silver performs cleaning and handles PII. Gold delivers business value.
- **Adopted naming:**
  - GCS: `gs://sample-store-data/bronze/{entity}/year=.../`
  - BigQuery datasets: `silver`, `gold`
  - dbt: `staging/stg_*`, `intermediate/int_*`, `marts/fct_*`, `marts/dim_*`

### ADR-004: Orchestration
- **Decision:** Dagster Cloud (Serverless plan)
- **Rationale:** Small team (2 engineers). Dagster has better DX than Airflow for small teams, clearer UI, native assets that facilitate lineage, and the serverless plan eliminates infrastructure overhead. Estimated cost: ~$50/month at current volume.
- **Accepted trade-offs:** Smaller plugin ecosystem than Airflow. Initial learning curve.
- **Discarded alternative:** Airflow (Cloud Composer) — $200+/month and operational overhead disproportionate for 2 engineers.

### ADR-005: Transformation
- **Decision:** dbt Core (open source) + BigQuery
- **Rationale:** All transformations are expressible in SQL. dbt offers versioning, native tests, documentation, and lineage at no additional cost. Volume does not justify Spark.
- **Accepted trade-offs:** dbt Core requires own CI/CD (no dbt Cloud web interface). Acceptable — GitHub Actions will be used.
- **Discarded alternative:** dbt Cloud — $50/month/developer. Unnecessary with GitHub Actions.

### ADR-006: Serving
- **Decision:** Metabase connected directly to BigQuery (Gold dataset)
- **Rationale:** Metabase is already a company-approved tool. Direct connection to BigQuery is simple and performant for current volume.
- **Accepted trade-offs:** No semantic layer — metrics defined in the Metabase dashboards themselves. If metric divergence becomes a problem, evaluate dbt Semantic Layer in the future.

## 6. Technical Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| PagSeguro API not approved before start of build | High | Medium | Financial reconciliation stories deferred to phase 2. Orders pipeline does not depend on it. |
| ERP duplicate bug worsens | Medium | High | Dedup by `order_id` implemented in Silver with log of discarded records |
| Black Friday volume (10x) breaks pipeline | Low | High | BigQuery scales automatically. Dagster configured with extended timeout for special-date jobs |
| Salesperson spreadsheet outdated | High | Low | Name normalization in Silver + monthly manual update process defined with HR |

## 7. What is outside this architecture

- Streaming / near-real-time — can be added in v2 if need arises
- PagSeguro integration — phase 2 after access approval
- Semantic layer (dbt Semantic Layer / MetricFlow) — evaluate if metric divergence becomes a problem
- Multi-region — out of scope due to cost and absence of requirement
